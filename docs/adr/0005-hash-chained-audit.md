# 0005 — Hash-chained, append-only audit with CI lints
**Status:** accepted

**Context.** Dataverse auditing is per-table opt-in, storage-metered, and Purview retention is 180 days without E5. KYC/AML needs 7 years, and an auditor's first question is "could an admin have edited this?".

**Decision.** `AuditEvent` has a monotonic `seq`, `prevHash` and `hash = sha256(prevHash + canonical fields)`. `audit()` is the only writer; DB triggers reject UPDATE/DELETE; `pnpm audit:verify` recomputes the chain and runs in CI and on the Audit and Compliance pages. `audit-lint` fails CI if a file mutates business tables without calling `audit()`, writes `AuditEvent` or the chain head outside `kit/audit.ts`, or opens a second Prisma client. Evidence packs (`/api/evidence/<control>`) bundle the matching events, the chain status and the role matrix per SOC 2 / PCI / GDPR control.

**Alternatives rejected.** Trusting the triggers alone (a DBA can drop a trigger; a hash break is visible); an external audit SaaS now (premature; the chain ships to the SIEM and object-locked storage in production).

**Amended 2026-10.** The first writer re-read the highest `seq` and relied on a unique-index violation plus retry. That is only correct outside a transaction: on Postgres a constraint error aborts the surrounding transaction, so the retry could never run inside the business mutation it was meant to be atomic with, and in practice no kit path passed a transaction at all. Now the first statement of every `audit()` is a blind write to a single `AuditChainHead` row (upsert + `seq` increment), so concurrent writers queue on that row lock instead of racing: no read-then-write upgrade (SQLite refuses those) and no constraint error, so it behaves the same on SQLite and Postgres and inside transactions. `audit()` always runs in a transaction (the caller's or its own), and every kit mutation (engine create/action, approval request/decision, settings, KYC decision) passes its transaction so state and audit event commit together. `audit:verify` also checks the head row matches the last event. The `seq` unique index stays as an independent second guard.

**Consequences.** Audit throughput is bounded by one row lock; fine for internal tools, and a Postgres sequence is no longer needed. Erasure requests must tombstone payloads without rewriting hashes; that procedure is a production gap. The lint is a smell detector, not a proof: atomicity comes from the transactions, not from the regex.
